How it works

      
A JWT is three Base64URL segments joined by dots: header.payload.signature. This tool splits the
      token, decodes the header and payload as UTF-8 JSON, and pretty-prints both. Standard timestamp claims
      (iat, nbf, exp) are additionally rendered as UTC dates with a human-readable
      span. The Bearer prefix and any whitespace are tolerated.

      
Why the signature is not verified

      
It could be — this tool just doesn't do it, by design. Client-side verification is entirely possible for
      asymmetric signatures (RS/ES/PS): the issuer's public key is meant to be public, and browsers can verify
      via WebCrypto. HMAC (HS*) verification is different — it needs the issuer's secret key, which must never
      be shared with a client. Pinning and trusting a public key inside a browser tool is real work (key distribution,
      rotation, revocation), so this tool keeps a narrower contract: decode-only, read-only, zero secrets — you inspect
      the token's contents, and verification stays with your backend or a library like jsonwebtoken.

      
Privacy

      
Decoding happens entirely in your browser. Nothing is transmitted, logged, or stored — you can disconnect from
      the internet and keep using this page.

    

    

      
Worked examples (synthetic — safe to paste)

      
Both tokens below are synthetic: no real issuer, no real user, no secrets. Decode does not verify a
      signature or grant any authorization — a decoded token is unverified data, and an expiry
      timestamp is a claim, not proof.

      
Example 1 — HS256 header with a synthetic (explicitly unverified) signature

      
eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiJleGFtcGxlLXRvb2xib3QiLCJuYW1lIjoiU3ludGhldGljIEV4YW1wbGUiLCJpYXQiOjE3MzU2ODk2MDAsImV4cCI6MTczNTc3NjAwMH0.c3ludGhldGljLXNpZ25hdHVyZS1ub3QtdmVyaWZpZWQtZG8tbm90LXRydXN0

      
Expected decode: header {"alg":"HS256","typ":"JWT"}; payload
      {"sub":"example-toolbot","name":"Synthetic Example","iat":1735689600,"exp":1735776000}.
      The claims rows show iat 1735689600 → 2025-01-01 00:00:00 UTC and exp
      1735776000 → 2025-01-02 00:00:00 UTC — exactly one day after issuance. The status line reads
      ✓ Decoded · alg HS256 · 4 payload claims · signature NOT verified: the signature bytes decode
      cleanly, but nothing was checked against any key. This token proves nothing about anyone.

      
Example 2 — unsecured token (alg "none", empty signature)

      
eyJhbGciOiJub25lIn0.eyJzdWIiOiJ1bnNlY3VyZWQtZGVtbyIsIm5vdGUiOiJzdHJ1Y3R1cmFsbHkgY29tcGxldGUsIGNyeXB0b2dyYXBoaWNhbGx5IHVuc2VjdXJlZCIsImlhdCI6MTczNTY4OTYwMH0.

      
Expected decode: header {"alg":"none"}; payload
      {"sub":"unsecured-demo","note":"structurally complete, cryptographically unsecured","iat":1735689600}.
      The status line warns ⚠ Decoded · alg none · UNSECURED token (empty signature, alg "none") — provides
      no authenticity at all. An unsecured token is structurally complete but offers zero integrity or
      origin guarantees — anyone can mint one. The iat row (2025-01-01 00:00:00 UTC) describes when
      the token claims to exist, nothing more.

      
Negative example — malformed signature

      
eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiJleGFtcGxlLXRvb2xib3QiLCJuYW1lIjoiU3ludGhldGljIEV4YW1wbGUiLCJpYXQiOjE3MzU2ODk2MDAsImV4cCI6MTczNTc3NjAwMH0.not$$valid$$base64url$$sig

      
Expected: rejection with ✗ Segment 3 (signature) is not valid Base64URL. (Syntax is checked here —
      authenticity is never verified by this tool.) — the tool reports syntax errors instead of guessing.

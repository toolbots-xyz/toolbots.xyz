# ToolBots — Deploy Guide (toolbots.xyz)

Launch runbook for publishing toolbots.xyz on GitHub Pages with Cloudflare free-plan DNS, plus analytics and uptime monitoring. Total cost: $0.

Every load-bearing fact below was verified against official documentation on **2026-09-07**; sources are listed in §9. Anything not confirmed against a primary source is marked **UNVERIFIED** inline.

Domain facts (from registrar WHOIS): `toolbots.xyz` registered at **eNom** (via DreamHost), expires **2027-08-20**, privacy-protected (Proxy Protection LLC / DreamHostDoNotDelete@proxy.dreamhost.com), nameservers currently `ns1/ns2/ns3.dreamhost.com`, no DNS records configured yet.

## 1. DNS records for GitHub Pages (apex domain)

GitHub Pages custom-domain DNS is **account-independent**: the apex A records point to GitHub's four anycast IPs regardless of whether the site lives in a user or organization account. The only account-dependent value is the **CNAME target**, which is `<account>.github.io` with **no repository name** — for the `toolbots-xyz` org, that is `toolbots-xyz.github.io`.

### 1.1 Apex domain `toolbots.xyz`

GitHub's docs table says to add **all** of the `A` **and** `AAAA` records below (or alternatively a single `ALIAS`/`ANAME` record). GitHub recommends keeping an `A` record even if you add `AAAA`, "due to slow adoption of IPv6 globally."

**A records** (required):

```text
toolbots.xyz.   IN  A  185.199.108.153
toolbots.xyz.   IN  A  185.199.109.153
toolbots.xyz.   IN  A  185.199.110.153
toolbots.xyz.   IN  A  185.199.111.153
```

| Type | Name (@ = apex) | Value |
|------|-----------------|-------|
| A | `@` | `185.199.108.153` |
| A | `@` | `185.199.109.153` |
| A | `@` | `185.199.110.153` |
| A | `@` | `185.199.111.153` |

**AAAA records** (IPv6 — GitHub now lists these in the same records table; adding them alongside the A records is the documented configuration):

```text
toolbots.xyz.   IN  AAAA  2606:50c0:8000::153
toolbots.xyz.   IN  AAAA  2606:50c0:8001::153
toolbots.xyz.   IN  AAAA  2606:50c0:8002::153
toolbots.xyz.   IN  AAAA  2606:50c0:8003::153
```

| Type | Name | Value |
|------|------|-------|
| AAAA | `@` | `2606:50c0:8000::153` |
| AAAA | `@` | `2606:50c0:8001::153` |
| AAAA | `@` | `2606:50c0:8002::153` |
| AAAA | `@` | `2606:50c0:8003::153` |

**ALIAS/ANAME alternative** (only if the DNS provider supports it and you skip A/AAAA):

| Type | Name | Value |
|------|------|-------|
| ALIAS or ANAME | `@` | `toolbots-xyz.github.io` |

### 1.2 `www` subdomain

GitHub recommends setting up `www` alongside the apex ("recommended for HTTPS secured websites"); GitHub Pages then auto-redirects between the two. Since `toolbots.xyz` is configured as the custom domain, `www.toolbots.xyz` will redirect to the apex.

| Type | Name | Value |
|------|------|-------|
| CNAME | `www` | `toolbots-xyz.github.io` |

The CNAME must point **directly** to `<organization>.github.io` — never `organization.github.io/repo`, never the raw Pages IP.

### 1.3 Verify DNS (after records exist)

```shell
dig toolbots.xyz +noall +answer -t A      # expect the four 185.199.x.153 IPs
dig toolbots.xyz +noall +answer -t AAAA   # expect the four 2606:50c0:800x::153
dig www.toolbots.xyz +nostats +nocomments +nocmd   # expect CNAME → toolbots-xyz.github.io
```

DNS changes can take up to 24 hours to propagate (GitHub docs).

**Wildcard warning (official):** do not use wildcard records like `*.toolbots.xyz` — GitHub warns they enable domain takeover even on a verified domain.

## 2. Verify the domain in GitHub (organization account)

Domain verification prevents takeover attacks (e.g., someone else publishing to `toolbots.xyz` after the Pages site is disabled/unlinked) and locks the domain + immediate subdomains to the `toolbots-xyz` org. Verification record details:

| Item | Value |
|------|-------|
| Where | **Organization settings** — not repository settings |
| Record type | **TXT** |
| Record name | `_github-pages-challenge-TOOLBOTS-XYZ` (exact org name GitHub shows you) |
| Record value | Unique token generated by GitHub when you add the domain |
| Verification window | Immediate up to 24 h after TXT is visible in DNS |
| After verified | **Keep the TXT record permanently** — the domain stays verified only while it exists |

Click path (org owner): profile picture → **Your organizations** → `toolbots-xyz` → **Settings** → sidebar, under "Code, planning, and automation" → **Pages** → **Add a domain** → enter `toolbots.xyz` → GitHub shows the exact TXT name/value → add that TXT at the DNS provider (Cloudflare, after §4) → check with:

```shell
dig _github-pages-challenge-TOOLBOTS-XYZ.toolbots.xyz +nostats +nocomments +nocmd TXT
```

then back on the same page: kebab menu (⋮) → **Continue verifying** → **Verify**.

> The literal org name in the TXT record is whatever GitHub displays when you add the domain (for the `toolbots-xyz` org, expected `_github-pages-challenge-toolbots-xyz`; confirm against the value GitHub actually shows).

## 3. GitHub Pages site setup

1. In the `toolbots-xyz` org, open the site repo (`toolbots.xyz` or `toolbots` — DNS is identical either way).
2. **Settings** → sidebar, "Code and automation" → **Pages**.
3. Under **Custom domain**, type `toolbots.xyz` → **Save**.
   - Branch publishing: this creates a `CNAME` file at the root of the publishing source (the repo already contains a `CNAME` file with `toolbots.xyz` — consistent).
   - GitHub Actions publishing: no `CNAME` file is created/needed.
4. GitHub starts an automatic DNS check. When DNS resolves to the Pages IPs (§1), GitHub provisions a free **Let's Encrypt** TLS certificate. A ✓ appears next to the custom domain when the cert is live.
5. **Enforce HTTPS**: once the certificate is provisioned, select **Enforce HTTPS** under "GitHub Pages". Per docs, it can take **up to 24 hours** for the option to become available after saving the custom domain; in practice the cert request commonly lands within about an hour (GitHub staff note in community discussion #23049).
   - All HTTP requests are then transparently redirected to HTTPS.
   - Cert provisioning restart: if stuck, click **Remove** next to the custom domain, retype it, **Save** — this cancels and restarts provisioning.
   - Constraint: the full domain must be < 64 characters for cert issuance (RFC3280 CN limit) — `toolbots.xyz` is fine.
   - After enforcing, keep all page assets on `https://` (no mixed content).

**Order matters:** add the custom domain in repo settings **before** configuring DNS records (GitHub's own ordering guidance, to prevent someone else claiming the domain at Pages in the window where DNS exists but GitHub doesn't know the domain is yours). Domain verification (§2) closes that window permanently.

**DNSSEC:** if DNSSEC is enabled at the registrar, it must be turned off **before** swapping nameservers (Cloudflare: changing NS with DNSSEC active can make the domain unreachable). This zone has no records and DNSSEC off is the default state — confirm during the NS change and re-enable DNSSEC through Cloudflare after activation if desired.

### 4.4 Wait for activation

- Cloudflare re-checks nameservers on a schedule: first check **60 seconds** after you update, then at gradually increasing intervals. You can re-trigger the check from the zone **Overview** page ("Check nameservers now").
- Typical activation: a few minutes to a few hours once the registrar change has propagated; Cloudflare's docs allow **up to 24 hours**. When the zone goes **Active**, Cloudflare emails you and the domain shows status **Active** under Domains.
- Verify independently:

```shell
dig NS toolbots.xyz @1.1.1.1     # expect the two <name>.ns.cloudflare.com servers
dig NS toolbots.xyz @8.8.8.8
```

### 4.5 Post-activation Cloudflare settings

1. **SSL/TLS → Overview**: leave the encryption mode at **Full** (or set **Full (strict)** — supported with Pages, since GitHub presents a valid publicly trusted Let's Encrypt certificate). Do **not** leave it on **Flexible** with an HTTPS-enforcing origin — see §5.
2. **SSL/TLS → Overview → Edge Certificates** tab: turn on **Always Use HTTPS** (available on Free). Requires the encryption mode to be anything other than **Off**.
3. **DNS**: confirm all GitHub records show the gray cloud (DNS only).

## 5. Proxied vs DNS-only for GitHub Pages — recommendation: **DNS only**

**GitHub-side reality:** GitHub's docs don't bless proxying Pages. GitHub staff guidance in the official community forum is to **disable Cloudflare's proxy (orange cloud) for any DNS records pointing at GitHub** so GitHub can see the real records for HTTPS-certificate issuance and renewal. A known failure mode: with records **proxied** and SSL mode **Full (strict)**, GitHub's Let's Encrypt renewal can fail — Cloudflare can't reach an origin whose cert it is masking, and GitHub validates that DNS points at Pages IPs (documented in `github/pages-health-check` issue #153). Users in the same threads report `Enforce HTTPS` never appearing until the cloud is flipped gray.

**The redirect-loop pitfall (if you do proxy):** Cloudflare's default encryption mode for a newly added zone is **Flexible**, which makes Cloudflare fetch the origin over plain HTTP. GitHub Pages with Enforce HTTPS answers every HTTP request with a 301 to HTTPS → Cloudflare re-issues HTTP → `ERR_TOO_MANY_REDIRECTS`. Cloudflare's own troubleshooting doc: loops occur when the mode conflicts with origin redirects, and the fix is **Full or higher** (or removing origin-side redirects).

**Decision for toolbots.xyz:**

| Setup | Verdict |
|-------|---------|
| **DNS only (gray cloud) — chosen** | GitHub Pages is already served over its own CDN (Fastly) with automatic HTTPS; Let's Encrypt issuance/renewal and Enforce HTTPS work without interference; zero loop risk; `dig` checks show real GitHub IPs, which also keeps GitHub's own DNS check green |
| Proxied + SSL mode **Full (strict)** + Always Use HTTPS | Works day one (Pages presents a valid public cert, so Full (strict) passes) and buys Cloudflare caching/DDoS features — but carries the documented cert-renewal and redirect-loop risks above; GitHub's DNS check may complain |
| Proxied + **Flexible** | Broken — guaranteed redirect loop once Enforce HTTPS is on. Never use |

If proxying is attempted later and `ERR_TOO_MANY_REDIRECTS` or a stalled cert appears: set SSL/TLS mode to **Full (strict)**; if cert issues persist, flip the GitHub records back to **DNS only**, wait for renewal, then re-proxied only at your own risk. **DNS-only is the fallback and the default recommendation.**

## 6. Cloudflare Web Analytics (free, cookieless)

Free on **all** plans; no cookies, no localStorage, no consent banner required; the beacon is < 4 KB. Limits: sites **proxied through Cloudflare** = unlimited; sites **not proxied** = up to **10**.

Two install modes (official get-started docs):

- **Proxied site (automatic injection):** if the hostname is proxied through Cloudflare, Web Analytics is enabled by default with no snippet — Cloudflare injects the beacon at the edge. Under **Manage site** you can switch between: automatic enable, enable but exclude EU visitor data, manual JS-snippet installation, or disable. *Note: with the DNS-only recommendation in §5, this mode won't apply to toolbots.xyz unless you proxy — use the manual path below.*
- **Manual snippet (our path, since records are DNS-only):**
  1. Cloudflare dashboard → **Web Analytics** (account-level, left sidebar) → **Add a site**.
  2. Enter hostname `toolbots.xyz` → confirm → **Done**.
  3. **Manage site** → copy the JS snippet. Format (per Cloudflare's FAQ):

     ```html
     <script
       type="module"
       src="https://static.cloudflareinsights.com/beacon.min.js"
       data-cf-beacon='{"token": "<YOUR_SITE_TOKEN>"}'
     ></script>
     ```

  4. Paste it into the site HTML. Official instruction: add the snippet to your HTML pages **before the ending body tag** (`</body>`) — Cloudflare's docs word it that way (the task brief's "before `</head>`" is also a common working placement, but the documented placement is end-of-body). Every page on toolbots.xyz: `index.html`, `404.html`, `tools/*/index.html`, and any Jekyll/templated layout so it lands on all pages.
  5. Data appears within a few minutes.

- **CSP:** if a Content-Security-Policy header/meta is ever added, whitelist `https://static.cloudflareinsights.com/beacon.min.js` in `script-src` (per the FAQ).
- Commit and push; verify the beacon loads (`curl -s https://toolbots.xyz/ | grep cloudflareinsights`).

Current limits/notes: no custom events/goals/funnels; Core Web Vitals reported (field data comes from Chromium-based browsers only); no alerting — pair with §7.
